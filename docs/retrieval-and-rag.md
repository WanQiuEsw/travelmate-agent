# 检索上下文优化与 RAG 改造建议

## 本次已实现

- 配置小红书后默认先搜社区攻略，仅在失败、无结果或核心主题未覆盖时检索知识库。节奏、行动与饮食约束用于规划；明确的兴趣及亲子、人文等主题仍会检查资料缺口。
- 知识库查询只补缺失主题。模型最多接收 2 段、每段 800 字符；小红书最多 5 条、每条 1200 字符；网页最多 4 条、每条 600 字符。资料正文总预算 10000 字符，均为字符限制，不是 token 限制。
- 正文仅在模型输入的 evidence 中出现一次，research 保留来源、检索状态和结构化交通结果。相同正文去重；节选标记 excerpt=true，不能把未展示内容推断成事实。
- 地点、天气、车次等结构化依据不截断；完整原始记录和版本快照继续保留，核验与导出读取原记录。模型输入预算不改变云端初召回参数。
- 预算先覆盖不同查询，再补同一查询的其他结果；同一查询优先采用最新记录，避免旧资料或单一主题占满上下文。
- 同一份存量案例的生成阶段 JSON 数据部分由 60131 字符降至 24709 字符，下降 58.9%。此对比保留了原有全部检索结果，未计入路由减少查询的额外收益；不代表整个 API 请求或实际 token、费用同比下降。
- thinking 继续关闭，32768 为输出上限，保留以避免完整攻略被截断。

## 现有知识库的实际基础

本地模式按城市文件筛选，把 Markdown 按空行切成段落，用查询与段落的共同字符数排序，取前三段。它没有 embedding，也没有独立语义重排。段落超过 1800 字符时截断，不能保证标题、条件及例外完整。

百炼模式已经请求向量召回 10 条、关键词召回 10 条，再重排返回 3 条。向量 TopK、关键词 TopK、重排 TopN 是不同阶段；本次的“最多两段进入模型”属于最后的上下文组装阶段。[百炼 Retrieve API](https://help.aliyun.com/en/model-studio/api-bailian-2023-12-29-retrieve)

仓库代码无法确认云端实际入库切片质量，也没有带正确依据标注的旅游问答评测集，因此目前不能声称 TopK 命中率或切片完整率达标。

## 应该补齐的知识与改造

| 环节 | 应理解什么 | 适合本项目的下一步 |
| --- | --- | --- |
| 数据与元数据 | 原文正确性、来源、更新时间、适用日期、城市及景点实体 | 为每段建立稳定 chunk_id，保留文档版本、标题路径、城市、景点、主题、时间与来源类型；过期内容更新或退出索引 |
| 切片 | 检索粒度与语义完整性并不相同 | 按“城市→景点→交通/预约/餐饮/避坑”章节切片，保留主语、条件、例外及表头；小片段用于召回，必要时回取父段或相邻段 |
| Embedding | 语义表示、相似度、中文表达及地名别名 | 用真实问法评测中文 embedding；统一入库和查询模型，模型或切片策略变化时对索引做版本管理 |
| 召回 | 关键词与向量各自擅长的匹配、过滤与查询拆分 | 本地升级为中文关键词/BM25与向量混合召回；城市、日期等明确条件先过滤，再按缺失主题查询 |
| 排序与组装 | Reranker、去重、证据覆盖与上下文预算 | 区分召回 K 与最终片段数 N；先扩大候选再重排，必要时补邻段，最终按主题覆盖和预算选取，避免重复段落占满上下文 |
| 生成与核验 | 有依据回答、引用是否支持结论、无依据时如何处理 | 回答与 chunk_id 可追溯；小红书作为社区体验，知识库作为参考，实时价格与开放状态仍独立核实 |
| 评估与运行 | 召回质量、回答质量、耗时、成本与失败诊断 | 固定评测集回归，记录查询、候选、入选片段及模型用量，区分“库里没有”“没召回”“排序靠后”“生成误用” |

切片应依据文档结构与查询类型评测；适量 overlap 可以帮助连续性，但增加 overlap 不能代替完整章节和例外条件。[切片说明](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents)

混合检索负责找候选，重排负责再判断候选与问题的相关性，两者解决的问题不同。[混合检索](https://learn.microsoft.com/azure/search/hybrid-search-overview)、[语义重排](https://learn.microsoft.com/en-us/azure/search/semantic-search-overview)

## TopK 怎样判断是否有效

TopK 是“取前几条”，不是命中率。先准备约 50～100 个代表性问题，标注正确依据所在片段和回答要点。包含城市重名、景点别名、不同日期、亲子/老人、资料不足及无答案场景。下面的参数只是实验起点，不是通用最佳值。

1. 对比召回 K=5/10/20 与最终 N=2/3/5。
2. 同时评估是否找全依据、正确依据是否排在前面，以及最终回答是否受依据支持。
3. 用相同评测集逐项调整切片、检索、排序，避免同时修改所有环节而无法归因。

| 指标 | 回答的问题 |
| --- | --- |
| Hit@K | 前 K 条中是否至少有一条正确依据？ |
| Recall@K | 标注的必要依据找回了多少？一个问题可能需要多段，命中一段未必足够 |
| Precision@K | 前 K 条中真正相关的占多少？ |
| MRR / nDCG | 正确或高相关依据是否排在前面？ |
| Faithfulness / 引用支持率 | 生成答案的结论是否受提供的证据支持？ |
| 无答案处理、耗时和用量 | 资料不足是否明确说明？质量提升是否值得新增耗时与成本？ |

检索评估与回答评估需要分开；Context Precision、Context Recall 与 Faithfulness 可参考 Ragas 的定义，自动打分也需要人工抽样核对。[Ragas 指标](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/)

建议先做评测集与切片抽检，再完善元数据、中文混合召回和重排；暂不引入新的向量数据库或模型服务。上下文字数节选解决的是输入膨胀，不能代替经过验证的语义切片。
